# Exact direct-matrix certificate schema v2

## Status and authority

Identifier: `PKF-EXACT-DIRECT-MATRIX-PILOT/2`.

This is the canonical Formal-owned version-2 schema for the mandatory Lean, Rust, and Mojo exact
direct-matrix certificate pilot. It is source-neutral and does not belong to KSD or another
computational owner. Lean independently checks the original bytes, exact semantics, theorem profile,
and both native records and alone emits the authoritative result. Rust and Mojo emit conformance
records only. Independent review identified release self-reference, native-variant classification,
route-independence, and native-record capacity defects; the corrected document passed focused
rereview and is frozen as the sole future implementation-target v2 schema.

This schema does not authorize implementation, toolchain installation, dependency addition,
execution, retention, commit, push, evidence promotion, or publication. It authenticates exact
synthetic bytes and propositions only; it does not authenticate origin, external source fidelity,
runtime execution, applicability, scientific adequacy, or publication status.

The required route identities, in fixed order, are:

1. `PKF-RUST-EXACT-DIRECT-MATRIX-CONFORMANCE/2`;
2. `PKF-MOJO-EXACT-DIRECT-MATRIX-CONFORMANCE/2`.

## Independent-route conformance requirement

A Phase 1 release conforms to this schema only when Rust and Mojo independently consume the original
body and envelope bytes and independently implement every parser, digest, canonicalization,
normalized-rational, and semantic operation used to produce their records. They must not share
parser code, generated schema code, digest code, rational-arithmetic code, semantic intermediates,
native libraries, foreign-function interfaces, or implementation-specific validation helpers.
Neither route may consume bytes or semantic values produced by the other route. Unavoidable shared
operating-system loaders, language runtimes, compiler targets, and dynamically linked system
libraries do not establish route independence and must be inventoried explicitly; none may supply a
shared parser, digest, rational, canonicalization, or semantic implementation.

Initial Rust and Mojo implementations must be produced in separate fresh contexts with access to
this normative schema but not to the other route's source until each route passes its independent
fixture suite. Cross-reading is permitted only during the later differential-review phase. These
independence facts are release-admission obligations: the Lean finalizer cannot infer them from the
native records. A retained external audit must verify them before the records are described as two
independent conformance routes. An authoritative Lean result binds the records and exact theorem
applications but does not itself attest implementation independence.

The unchanged sub-schema identifiers deliberately remain
`PKF-EXTERNAL-MATRIX-FRAME-BINDING/CANDIDATE-1`, `PKF-CANONICAL-BINARY/1`,
`PKF-DIRECT-HERMITIAN-PAIR/1`, and the matrix semantic-digest domain ending in `/matrix/v1`.
Version 2 changes the package/result lifecycle, not those sub-schema meanings. Their unchanged
identities make that distinction explicit rather than silently relabeling unchanged semantics.

## Canonical package shape

A pilot package is a directory containing exactly two regular files:

```text
body.pkfb
authentication.pkfa
```

Symlinks, devices, archives, additional files, path traversal, remote references, and external
payload references are outside the schema. File names are transport labels, not identity. The
checker authenticates the bytes and the package identity inside `body.pkfb`. Replay and checker
results are written outside the two-file input directory and cannot modify it.

The body uses `PKF-CANONICAL-BINARY/1`. The envelope uses
`PKF-DETACHED-AUTHENTICATION/1`. Both encodings are fixed-field binary records. They are not
self-describing extensible maps. A field addition, field removal, reordered field, changed primitive
encoding, new scalar class, or changed digest preimage requires a new major identifier.

### Primitive encodings

All byte strings below are concatenated without padding or alignment.

| Primitive | Canonical encoding |
|---|---|
| `octet` | one byte |
| `nat` | unsigned LEB128, shortest encoding only, maximum value `2^32 - 1` |
| `raw` | `nat` byte length followed by exactly that many bytes |
| `ascii` | `raw` whose bytes are all in `0x20`--`0x7e`; identities must be nonempty and have no leading or trailing ASCII space |
| `magnitude` | `raw` big-endian unsigned magnitude; zero is empty; nonzero values have no leading zero byte |
| `integer` | one sign octet (`0` nonnegative, `1` negative) followed by `magnitude`; zero must use sign `0` |
| `positive` | nonempty `magnitude` with value greater than zero |
| `rational` | `integer` numerator followed by `positive` denominator |
| `complex-rational` | `rational` real part followed by `rational` imaginary part |
| `sequence<T>` | `nat` element count followed by exactly that many canonical `T` values |
| `option<T>` | octet `0` for absent or octet `1` followed by one canonical `T`; every other tag rejects |

Every rational must be normalized: denominator positive, numerator and denominator coprime, and zero
encoded as numerator zero with denominator one. The parser rejects negative zero, denominator zero,
nonminimal LEB128, leading magnitude zeros, unreduced fractions, truncation, trailing bytes, and any
value exceeding a declared resource bound.

`ascii` preserves exact bytes; it does not perform Unicode normalization because non-ASCII text is
not admitted. Ordered carrier labels must be unique byte strings.

Matrix dimensions are derived from the single carrier cardinality and are not repeated. The fixed
entry count prevents missing, duplicate, or excess entries. Matrix A and B share the same carrier,
space, basis, scalar unit, and energy-reference identity by construction. A producer cannot supply
norms, eigenvalues, aggregate errors, Hermiticity flags, or theorem conclusions.

The UUID syntax check does not prove global uniqueness. Phase 1 binds the declared package identity
to bytes and rejects duplicate identities within one batch. Cross-run replay and global uniqueness
remain ledger obligations outside this repository; the audit record must say so.

signature.

### Digest preimage

Let `body_bytes` be the complete bytes of `body.pkfb`, including its magic and end marker. The only
accepted digest is:

```text
SHA-256(
  UTF8("PKF-EXTERNAL-MATRIX-FRAME-BINDING/body/v2")
  || BYTE(0x00)
  || body_bytes
)
```

The detached envelope, digest bytes, and any future signatures are excluded from the preimage. The
contract, pilot schema, canonicalization identity, theorem revision, profile, semantic identities,
and all matrix entries are inside `body_bytes` and are therefore bound. The implementation must
compare all 32 digest bytes without accepting prefixes or case-encoded text.

SHA-256 establishes byte identity under its standard cryptographic assumption. It does not prove
producer correctness, origin, global package uniqueness, or scientific applicability.

## Exact semantic decoding

For cardinality `n`, decoding constructs the carrier `Fin n`. Label `labels[i]` is metadata bound to
index `i`; it does not create a new quotient or inferred ordering.

A normalized rational pair `(p, q)` first denotes a computational retained rational value with
arbitrary-size integer numerator and positive denominator. A retained complex value is the pair
`QComplex = (re, im)` of those rationals, with computational equality, negation, subtraction,
conjugation `(re, im) ↦ (re, -im)`, and norm square `re^2 + im^2`.

The row-major entry at offset `i*n + j` denotes a retained rational-complex matrix entry `(i, j)`.
No transpose, conjugation, column-major option, one-based index, or source-format convention exists
in Phase 1.

Hermiticity is executed on the retained representation, not by invoking equality on `ℂ`:

```text
A.re[i,j] = A.re[j,i]  and  A.im[i,j] = -A.im[j,i]
B.re[i,j] = B.re[j,i]  and  B.im[i,j] = -B.im[j,i]
```

Only after those checks succeed does the semantic map cast each retained entry to

```text
((re : ℚ) : ℂ) + ((im : ℚ) : ℂ) * Complex.I.
```

The implementation must prove that the cast commutes with conjugation and that successful retained
Hermiticity implies `A.IsHermitian` and `B.IsHermitian` for the cast matrices. It must not rely on
Mathlib's noncomputable classical complex equality as an executable decision procedure. The exact
Frobenius-power audit uses the retained rational formula
`sum i,j, ((A.re-B.re)^2 + (A.im-B.im)^2)` and a bridge theorem to the cast complex norm-square sum.
A producer-supplied assertion cannot satisfy any premise.

unnormalized square-sum theorem before its normalized consequences. Eigenvalues use Formal's
canonical decreasing, multiplicity-retaining carrier. No eigensolver array is an input or output.

Phase 1 proves the theorem propositions for the decoded exact matrices. It does not claim a concrete
rational value for the matrix `L2Operator` norm, the Frobenius norm, a square root, or an eigenvalue.
The exact rational entrywise Frobenius power

```text
sum i, sum j, normSq((A-B)[i,j])
```

may be computed independently as audit data, because rational complex `normSq` is rational. That
computed value must be derived by the checker and cannot replace the theorem conclusion.

## Checker and finalization pipeline

The transport wrapper admits an invocation only when every original or native input length is at
most `2^32 - 1`; otherwise it returns `INPUT_LENGTH_OUT_OF_DOMAIN` and emits no authoritative
result. The body and envelope semantic limits remain 1 MiB and 64 KiB respectively. Each native
record has a 2 MiB semantic limit.

Lean checks body and envelope size, canonical syntax, repeated identities, digest, source class,
Formal revision, theorem profile, carrier, semantic identities, retained rational entries, exact
Hermiticity, all five theorem applications, and exact Frobenius-power audit data in that order. No
later gate may repair, normalize, reorder, reduce, transpose, conjugate, or infer missing input.

After Lean's exact checks succeed, it inventories both fixed native inputs, classifies both route
audits, and selects the final disposition under the precedence below. Lean reparses every present
within-limit native record; a producer-supplied comparison flag is never trusted.

`theorem-binding-result` is, in order: declaration ID `ascii`; module `ascii`; fully qualified
declaration name `ascii`; conclusion-class octet (`0` pointwise, `1` maximum, `2` square-sum,
`3` squared RMS, `4` RMS); and instantiation octet (`0` fail, `1` pass). Its sequence must equal the
five-row theorem table byte for byte and in order. This gives maximum, square-sum, squared-RMS, and
RMS conclusions distinct fixed records.

`native-route-audit` begins with the expected route identity `ascii` and a state octet. State `0`
is missing and has no payload. State `1` is present but over 2 MiB and contains only actual length as
`nat`. State `2` is present within limits but noncanonical and contains actual length then ordinary
file `sha256`. State `3` is canonically parsed and contains actual length, ordinary file `sha256`,
record-schema identity, declared route identity, implementation commit/tree, toolchain identity,
claimed executable digest, route outcome, route-reason sequence, release-identity comparison,
input-byte comparison, and `option<octet>` semantic comparison. Comparison octets are `0` fail or
`1` pass; semantic comparison is present exactly when the declared native payload is present.

The state classification is frozen. After the length test, the finalizer parses fields 1--15 in
wire order. Any primitive-canonicality failure, wrong magic, wrong record-schema identity, malformed
end marker, trailing byte, route outcome outside `0` or `1`, reason outside codes 0--26 or 29, or
violation of the outcome/reason/payload shape is state `2`. The required shapes are exactly: pass
means outcome `0`, zero reasons, and a present payload; fail means outcome `1`, one allowed reason,
and an absent payload. Only a record satisfying all those record-level rules reaches state `3`.
Within state `3`, the declared route identity is compared with the expected input position; release
identity, original-input bytes, and every declared payload value are compared independently. A
wrong route, implementation revision, toolchain identity, original-input binding, or payload value
therefore remains state `3` with the applicable comparison octet zero and is a failing audit. The
name `native-validated-payload` denotes the pass-variant wire field; Lean never trusts that name or
producer assertion and sets semantic comparison to pass only after comparing every payload field.

`axiom-audit-entry` is, in order: fully qualified checker/soundness declaration name `ascii`;
admission octet (`0` none, `1` present); and a bytewise-sorted, duplicate-free `sequence<ascii>` of
axiom names. The top-level audit sequence is bytewise sorted by declaration name, duplicate-free,
and must match a checker-embedded axiom/admission manifest. Accepted output requires a nonempty
audit, admission octet zero in every entry, and every axiom name in the closed set `propext`,
`Classical.choice`, or `Quot.sound`. This record reports the build-bound manifest entries; it does
not cause Lean to inspect its own environment at runtime.

The eight set nonclaim bits mean, from least-significant to most-significant bit: producer origin not
authenticated, global UUID uniqueness not proved, external source fidelity not checked, runtime
arrays absent, eigensolver output absent, applicability not assessed, scientific adequacy not
assessed, and publication not authorized.

For reason code 0 all three original-input digest options are absent, preventing resource rejection
from forcing a full read or hash of oversized original input. For every other disposition they are
present. Accepted output requires no reason, a passing semantic record, a present route-audit option
containing two state-3 audits with passing outcomes and comparisons, and a conforming axiom audit.
Unresolved output requires sole reason 27, a passing semantic record, present route audits, no failed
route, and at least one state-0 route. Rejected native output requires reason 28, a passing Lean
semantic record, present route audits, and at least one failing route audit. Rejected core output uses
codes 0--26 and has absent semantic and route-audit options. These variant
rules eliminate implicit or implementation-selected missing values.

For any matrix `M`, its semantic digest is
`SHA-256(UTF8("PKF-EXACT-DIRECT-MATRIX/matrix/v1") || BYTE(0x00) || nat(n) || entries(M))`,
where `entries(M)` is the row-major sequence of normalized canonical `complex-rational` encodings
without a sequence count. The difference digest uses checker-derived normalized entries of `A-B`,
not producer bytes. A human-readable report is derived from the authoritative result and has no
independent authority.

## Native conformance files

Native records are lifecycle inputs to the Lean finalizer and remain outside the two-file package:

```text
rust-conformance.pkfc
mojo-conformance.pkfc
```

Each file is at most 2 MiB and uses `PKF-NATIVE-CONFORMANCE-RECORD/2`. The top level is deliberately
variant-shaped so an independently detected syntax or semantic failure can be represented without
inventing unavailable semantic fields:

| Order | Field | Exact encoding |
|---:|---|---|
| 1 | magic | eight literal ASCII octets `PKFNCR02` |
| 2 | record schema | `ascii`, exactly `PKF-NATIVE-CONFORMANCE-RECORD/2` |
| 3 | declared route identity | `ascii`, exactly one of the two fixed route identities; the finalizer separately compares it with the identity expected from the ordered input position |
| 4 | implementation commit | exactly 20 literal bytes |
| 5 | implementation tree | exactly 20 literal bytes |
| 6 | toolchain identity | nonempty `ascii`, at most 256 bytes |
| 7 | claimed executable digest | exactly 32 literal SHA-256 bytes |
| 8 | body byte length | `nat`, equal to the original body file length |
| 9 | ordinary body digest | exactly 32 literal SHA-256 bytes |
| 10 | envelope byte length | `nat`, equal to the original envelope file length |
| 11 | ordinary envelope digest | exactly 32 literal SHA-256 bytes |
| 12 | route outcome | octet `0` pass or `1` fail |
| 13 | route reasons | `sequence<nat>` of count zero for pass and count one for fail |
| 14 | validated payload | `option<native-validated-payload>`; present if and only if route outcome is pass |
| 15 | end marker | eight literal ASCII octets `ENDNCR02`, followed by end of file |

A route failure reason is the first applicable `/2` core reason code 0--26 under the same precedence
as Lean, or code 29 `NATIVE_INTERNAL_FAILURE` when the route cannot complete despite canonical
within-limit input. Code 29 must never be used to mask a more specific 0--26 failure.

`native-validated-payload` has this exact order:

| Order | Field | Exact encoding |
|---:|---|---|
| 1 | package identity | canonical UUID `ascii`, equal to the body value |
| 2 | domain-separated body digest | exactly 32 literal SHA-256 bytes under the `/2` rule |
| 3 | theorem commit | exactly 20 literal bytes, equal to the body theorem commit |
| 4 | theorem tree | exactly 20 literal bytes, equal to the body theorem tree |
| 5 | theorem profile | `ascii`, exactly `PKF-DIRECT-HERMITIAN-PAIR/1` |
| 6 | carrier identity | `ascii`, equal to the body value |
| 7 | carrier cardinality | `nat`, equal to the body value |
| 8 | ordered carrier labels | `sequence<ascii>`, byte-for-byte equal to the body labels |
| 9 | space identity | `ascii`, equal to the body value |
| 10 | basis identity | `ascii`, equal to the body value |
| 11 | scalar-unit identity | `ascii`, equal to the body value |
| 12 | energy-reference identity | `ascii`, equal to the body value |
| 13 | matrix A role | `ascii`, exactly `candidate` |
| 14 | matrix B role | `ascii`, exactly `reference` |
| 15 | matrix A semantic digest | exactly 32 literal bytes under the matrix preimage rule |
| 16 | matrix B semantic digest | exactly 32 literal bytes under the matrix preimage rule |
| 17 | difference semantic digest | exactly 32 literal bytes for independently derived `A-B` |
| 18 | matrix A Hermiticity | octet `0` fail or `1` pass; pass is required for a validated payload |
| 19 | matrix B Hermiticity | octet `0` fail or `1` pass; pass is required for a validated payload |
| 20 | entrywise Frobenius power | normalized `rational`, independently derived |
| 21 | semantic operation count | `nat`, exactly `6*n*n` |

The implementation commit/tree and toolchain identity must match the Lean finalizer's build-bound
release descriptor defined below. The claimed executable digest is bound into the record and result
for external audit but is not compared by Lean: embedding an expected native executable digest into
the same source revision would create a release-build self-reference without authenticating which
binary actually ran. The retained conformance procedure must independently hash the invoked
executable and compare it with the claimed value. Phase 1 states explicitly that Lean's result does
not prove that this procedure occurred.

## Release-manifest boundary

A retained release descriptor is generated only after the checker and native source revisions
already exist. It is an authenticated build input outside every Git revision that it names. The
build compiles its values into the Lean finalizer; the finalizer never loads a mutable runtime
manifest. The descriptor contains:

1. result and native-record schema identities;
2. the two fixed route identities in order;
3. the immutable checker source commit and tree claimed in result fields 10 and 11;
4. one immutable implementation source commit and tree for each native route;
5. one exact nonempty toolchain-identity byte string for each native route; and
6. the sorted axiom/admission audit entries required by the result schema.

The native implementation revisions need not equal the later checker revision and must not contain
pins to their own commit or tree. The finalizer uses descriptor items 2, 4, and 5 for each route's
release-identity comparison and emits item 3 as an externally auditable source-identity claim. It
uses item 6 for the axiom/admission audit. Because the descriptor is outside the revisions it names,
no Git object is required to contain its own hash.

The descriptor contains no expected finalizer or native executable digest. Changing the descriptor
changes the built executable and therefore its externally measured digest; it does not require or
claim a different source revision. Before release admission, an external retained procedure must
authenticate the descriptor, verify clean checkouts at all claimed revisions and trees, verify the
build inputs and toolchains, hash the invoked executables, and bind those executable digests to the
invocation record. Neither the embedded descriptor nor the authoritative Lean result proves that
this external provenance procedure occurred. This boundary avoids both a Git source fixed point and
a source/binary digest cycle without silently changing the wire schema.

## Frozen semantic-operation schedule

For each matrix entry in row-major order, every route performs exactly:

1. normalized rational subtraction for the real component of `A-B`;
2. normalized rational subtraction for the imaginary component;
3. normalized multiplication squaring the real difference;
4. normalized multiplication squaring the imaginary difference;
5. normalized addition forming the entry norm square; and
6. normalized addition into the row-major accumulator.

The record therefore emits exactly `6*n*n`, at most 1,536. Rational canonicality checks,
Hermiticity sign/denominator comparisons, digest operations, and internal GCD or multiplication
steps are not semantic operations. A failed preflight allocation does not increment the count.
Normalized input magnitudes remain bounded by 256 bytes; normalized derived and emitted magnitudes
are bounded by 1 MiB. Exceeding a derived magnitude bound is `RESOURCE_BOUND_EXCEEDED` in the Lean
route and a failing native outcome in a conformance record.

### Derived-magnitude bound justification

A 256-byte input magnitude is strictly less than `2^2048`. Before normalization, one rational
subtraction therefore has numerator magnitude less than `2^4097` and denominator less than
`2^4096`. Squaring gives numerator less than `2^8194` and denominator less than `2^8192`. Adding the
real and imaginary squares gives an entry numerator less than `2^16387` and denominator less than
`2^16384`.

For `K ≤ n*n ≤ 256` entry norm squares, the unreduced common-denominator construction is bounded by
`2^(16384*K)` in the denominator and by `K * 2^(16384*K + 3)` in the numerator. At `K = 256`, both
magnitudes require fewer than 524,291 bytes. Every normalized sequential intermediate is bounded by
the corresponding prefix construction, and normalization can only reduce numerator and denominator
magnitudes. The 1 MiB per-magnitude limit therefore has more than a factor-of-two byte margin under
the frozen dimension and input bounds.

The largest native payload contains one such rational. Its sign byte, two canonical length prefixes,
and two maximal magnitudes occupy fewer than 1,048,590 bytes. Summing every other fixed field and
every field-specific maximum in the native record contributes less than 64 KiB, including sixteen
64-byte labels and all bounded identities. The 2 MiB native-file ceiling therefore exceeds the
complete maximum encoded passing record, not merely either rational magnitude. These are arithmetic
and serialization safety arguments, not scientific or theorem hypotheses.

## Cycle-free lifecycle

1. Lean reparses the original body and envelope and may emit an unresolved result with two missing
   route audits.
2. Rust independently reads only the original body and envelope and writes its native record.
3. Mojo independently reads only the original body and envelope and writes its native record.
4. Lean reparses the original files and both raw native files, reconstructs both route audits, and
   emits the final authoritative result.

Native files do not contain the authoritative result digest, each other's digest, or values copied
from another native route. The final result may bind both native file digests because it is created
last. Re-running the same finalizer executable does not alter any input and reproduces identical
bytes when its compiled release descriptor and all four input files are unchanged.

## Resource limits

- body: at most 1 MiB;
- envelope: at most 64 KiB;
- native conformance file: at most 2 MiB;
- identity or description string: at most its field-specific limit and never more than 4 KiB;
- sequence count: at most 4,096 before field-specific checks;
- carrier cardinality: at most 16;
- matrix entries: exactly `2*n*n`, at most 512;
- input rational numerator or denominator magnitude: at most 256 bytes;
- normalized derived or emitted rational numerator or denominator magnitude: at most 1 MiB; and
- one package per invocation unless a batch wrapper supplies an external duplicate-ID set.

The exact schedule performs six normalized rational operations per row-major entry: two difference
subtractions, two squares, one norm-square addition, and one accumulator addition. The semantic
operation count is exactly `6*n*n`, at most 1,536. Canonicality checks, Hermiticity sign and
denominator comparisons, digest operations, internal GCD steps, and failed preflight checks do not
add semantic operations. Before allocating a normalized result, each route preflights the 1 MiB
magnitude cap where its integer API permits. Internal algorithms may differ, but the six normalized
checkpoints and row-major accumulator order may not.

## Required fixtures

Formal may retain only self-contained synthetic fixtures. Every acceptance fixture needs hand-
auditable source expressions, canonical body and envelope bytes, expected digests, both expected
native records, and the expected authoritative result.

### Acceptance fixtures

1. `dimension-one-equal`: equal `1 x 1` rational Hermitian matrices;
2. `dimension-two-real`: distinct real symmetric `2 x 2` matrices;
3. `dimension-two-complex`: noncommuting complex Hermitian matrices with nonzero imaginary
   off-diagonal entries;
4. `dimension-three-repeated-spectrum`: a Hermitian pair with repeated eigenvalues and no eigenvector
   labels; and
5. `dimension-sixteen-boundary`: sparse matrices at the dimension limit.

### Core adversarial fixtures

At minimum cover:

- the transport boundary at `2^32 - 1` and an abstracted larger length returning
  `INPUT_LENGTH_OUT_OF_DOMAIN` without a result;
- every truncated primitive and field boundary;
- nonminimal LEB128;
- magnitude leading zero, negative zero, zero denominator, negative denominator encoding, and
  unreduced rational;
- invalid ASCII, overlong strings, malformed UUID, duplicate labels, zero dimension, and dimension
  17;
- missing or excess entries and reordered, transposed, or conjugated entries with a stale digest;
- changed body with stale digest and changed envelope identity with unchanged body;
- digest prefix, wrong algorithm, nonzero signature count, and trailing bytes;
- wrong Formal commit, tree, profile, role, basis, unit, or energy-reference identity;
- non-Hermitian A, non-Hermitian B, and tolerance-small but exactly nonzero asymmetry;
- producer-supplied norm, eigenvalue, or diagnostic bytes as unsupported trailing bytes;
- duplicate package identity at the external batch-wrapper boundary; and
- multi-failure inputs at every precedence boundary, asserting one prescribed reason and exactly
  reproducible result bytes.

### Native-route adversarial fixtures

At minimum cover:

- both native records missing;
- Rust missing with Mojo passing;
- Mojo missing with Rust passing;
- Rust failing with Mojo missing, demonstrating failure dominance;
- Mojo failing with Rust missing, demonstrating failure dominance;
- both failing, demonstrating Rust-first reporting while retaining both audits;
- wrong route order and duplicate route identity;
- stale body or envelope digest in exactly one native record;
- wrong implementation commit, tree, or toolchain identity, each rejecting;
- mutated claimed executable digest, which changes bound bytes but does not by itself change Lean's
  disposition and must be caught by the external invocation-provenance audit;
- one noncanonical native file and one passing file;
- one native file over 2 MiB without forced hashing;
- semantic disagreement in each matrix digest, Hermiticity flag, Frobenius power, and operation count;
- exact `6*n*n` operation counts at `n = 1` and `n = 16`; and
- a byte-for-byte deterministic final accepted result with both routes passing.

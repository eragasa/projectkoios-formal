# Lean architecture

## Role

Lean is the mathematical and acceptance authority of `projectkoios-formal`. It owns:

- canonical original-byte decoding or a proved equivalent decoding boundary;
- domain-separated authentication;
- exact certificate semantics;
- transport from computational rational-complex values to `ℂ`;
- exact Hermiticity and derived-quantity lemmas;
- instantiation of the pinned ordered-spectrum theorems;
- validation and binding of both required native conformance records;
- the final authoritative disposition and result; and
- checker/result soundness plus axiom and admission reporting.

A Rust or Mojo conformance record is not a Lean theorem. Native agreement is a mandatory Phase 1
acceptance premise, but it cannot replace Lean authentication, semantic soundness, or theorem
application.

## Source layout

Lean source remains in the existing Lake layout:

```text
ProjectKoios/
├── Formal/
└── BandGauge/
```

The exact module path for certificate-binding code must be frozen during the implementation Gate 0
layout amendment. Existing modules must not be moved into a new `lean/src/` tree.

## Planned checker boundary

The Lean route must independently cover:

1. canonical primitive decoding from the original body and envelope bytes;
2. domain-separated package authentication;
3. normalized rational-complex semantics;
4. exact Hermiticity and matrix-role checks;
5. derivation of differences and Frobenius quantities;
6. theorem-profile conclusions;
7. canonical parsing and comparison of the Rust and Mojo conformance records; and
8. final disposition under the frozen missing/failure precedence.

If any original-byte step is left to a native executable, it becomes an explicit trusted boundary and
must not be described as kernel-checked. Native records must be data inputs to a Lean finalizer, not
assumptions or foreign proof objects.

## Validation

Lean changes require at minimum:

- a clean Lake build;
- explicit `#print axioms` coverage for public checker, finalizer, and soundness declarations;
- no `sorry`, `admit`, custom axiom, or opaque external premise;
- immutable Lake dependency revisions and recorded toolchain identity;
- standard and domain-separated digest vectors; and
- cross-language fixture agreement without importing Rust, Mojo, or Python results as theorem
  assumptions.

## Current status

The mathematical theorem profile exists. The byte parser, SHA-256 implementation, executable
checker, native-record parser, authoritative finalizer, result parser, and cross-language binding
theorems do not exist.
